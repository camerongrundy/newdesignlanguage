Header Navigation

Calypso’s header is the only chrome that persists across every product. It carries the brand, the account you are working in, the sections of the current product, and the signed-in user — in that order, top to bottom. The one on this page is the live component; the controls below drive it.

Try it

Expanded · 238px

Watch the header on the left as you press these. Every control is the same one a person would use directly — nothing here is a mock.

Anatomy

    This one is a facsimile, not the real header — it is here so you can poke at every region without leaving the page. Hover a number to light up the part it names, and press anything in the model: the toggle collapses it to a rail, the switcher and the avatar open their menus, and the section list moves its active state.

    Two widths

    Expanded

    238px

    The default. Section names are readable at a glance, the account in use is stated in words, and the signed-in user is named. Use it anywhere the content area has room to spare — dashboards, settings, anything under about eight columns of table.

    Labels at 14px/500, 9px vertical padding, 8px radius, 2px between items.

    Rail

    68px

    Trades names for 170px of content width. Every section keeps its icon, the brand clips to the mark, the account becomes an icon button and the user becomes their avatar. Reach for it on wide tables and anything horizontally scrolling.

    Icons at 17px, centred, tooltip on hover and focus. Menus open to the right of the rail.

    The rail is a width change, not a different component — same markup, same handlers, one class on the shell. Anything that only exists in one of the two states is a bug, which is why the collapsed state keeps tooltips rather than dropping the labels outright.

    03

    Buttons

    Calypso ships three levels of emphasis — primary, secondary, tertiary — plus a destructive pair, each at 8px radius. Every one takes a leading icon, a trailing icon, both or neither, and the outlined variants have been recontrasted so their edges actually clear WCAG against the page background.

    Variants

    Primary
    Secondary
    Tertiary
    Destructive
    Destructive outline

    One primary per view. If a screen seems to need two, one of them is secondary. Tertiary carries no boundary, so it is only for actions sitting inside a container that already has one — a card, a toolbar, a table row. Filled destructive is for the confirming press, typically the last thing in a dialog; the outline is for the action that opens that dialog, sitting in a toolbar or a row where a solid red would shout across the whole page.

    Sizes

    Default · 40px
    Small · 32px

    Small is for dense surfaces — table toolbars, card headers, inline row actions. Anything a person is meant to find without looking for it stays at the default size.

    States

    Hover and focus are live above — tab through the row to see the ring. The focus ring is 2px of --accent at a 2px offset, so it lands on the page background rather than on the button, which is what keeps it at 3:1 even against the primary fill.

    Contrast audit

    Pair Foreground Background Ratio Required Result

    The outlined buttons were the problem worth fixing. A border only counts as a boundary if it clears 3:1 against what sits next to it — WCAG 2.2 SC 1.4.11 — and the old --border-input at #CFCFCF managed 1.49:1 on this background. It read as a boundary to anyone with full colour vision and vanished for everyone else. #858C99 clears it on both the page background and a white card, so the same token works wherever the button lands. Disabled controls are exempt from both rules, but the label is kept above 4.5:1 anyway so the state stays readable.

    05

    Tabs

    Two switching patterns, each with a job. Raised tabs partition a page; the segmented control toggles between views of the same records. Both are keyboard-driven with arrow keys.

    Raised tabs — page-level partitions

    Section One

    The selected tab lifts onto a white surface with a soft shadow; unselected tabs are transparent and take a 66% white wash on hover. Nothing moves horizontally, so the row never reflows as you click across it.

    Section Two

    Each panel is a plain region. Panels are hidden with the hidden attribute rather than display:none in CSS, so assistive tech and in-page search agree with what is on screen.

    A Much Longer Section Name

    Selection persists per tab group. Arrow Left and Arrow Right move focus and selection; Tab moves out of the group entirely, which is the WAI-ARIA automatic-activation pattern.

    Section Four

    Tab labels wrap to a second line rather than scrolling or truncating — a long label has to stay legible at 360px.

    Segmented control — one dataset, two views

    The pressed segment takes the white surface and a two-layer shadow. Reach for this only when the options are views of the same records — if the content differs, it is a tab.

    Loading States

    Every control that starts work has to say so before the work finishes. The rule across Calypso is the same one: the control stays put, takes the disabled treatment, swaps its label to the present tense and shows the progress mark. Nothing reflows, nothing disappears, and the text carries the meaning for anyone who cannot see the motion.

    10

    Error States

    An error has one job: tell the person what happened, where, and what to do next. Calypso puts the message beside the thing that failed, keeps whatever they had typed, and always offers the way forward. Nothing is thrown away because a request came back badly, and nothing blames the person for a system that did not answer.

    Field validation

    The name shown in lists and reports.
    Enter a whole number. This looks like it contains the letter O.
    Validated when you leave the field, not while you type.

    The message sits under the field it belongs to, is tied to the input with aria-describedby, and replaces the help text rather than stacking on it. Validation runs on blur, never per keystroke — telling someone their email is invalid while they are still on the third character is noise, not help. The value they typed is never cleared.

    Form-level summary

    This record could not be saved — 3 fields need attention
    • People covered — must be a whole number
    • Connections — cannot be higher than people covered
    • Assigned period — choose a period before saving

    Shown only after a submit attempt, at the top of the form, with each item linking to its field. On a long form the failing field is often off screen; a summary is the only thing that gets someone to it. It takes role="alert" so it is announced when it appears.

    When an action fails

    Run a failing save Working → failed → retry. The control keeps its place and the reason sits beside it.
    Couldn’t save — the server didn’t respond.

    A row that failed to save In progress / Concept

    The counterpart to the saving row in the previous section. The edit is not discarded: the value the person chose stays on screen, marked as unsaved, with Retry and Discard sitting in the cell that failed rather than in a separate actions column — on a wide table the recovery belongs beside the thing that needs recovering, not a thousand pixels away from it. Reverting the cell silently and showing a toast is how people lose work without noticing. Only the failed row is marked — the rest of the table is unaffected, because one failed write is not an outage.

    One card failing takes down that card. Replacing the whole screen with an error page because a sidebar widget timed out costs everything else that did load.

    A banner, not a toast. A connection problem lasts longer than four seconds, so the notice has to stay until the condition clears — and it has to say what happens to work in progress.

    Three things that look alikeTell them apart
    Nothing here yetNo records have been added. Add the first one.
    No accessYour account can’t view this list. Ask an administrator for the Records role.

    Empty, forbidden and broken need three different messages. Collapsing them into “No records found” sends someone to rebuild a filter when the real answer is that they need a permission.

    Destructive confirmationBefore, not after
    Remove 24 records from this list? They stay in the account and can be added back. This doesn’t delete any data.

    The confirm button names the thing and the count, never “OK”. Say what is reversible; people hesitate over safe actions when the copy is vague about it.

    Customer Pain Points

    What follows is why this system exists. Each item is a behaviour we can see in product data, the change Calypso makes in response, and a working piece of that change to try. None of this is cosmetic.

    01

    Pain Point #1 - The Next/Previous arrows on our tables are the single biggest source of rage clicks in the product. While we do have filters and search nested within our tables, lower tech users seem are opting to click through the pages individually one at a time using the arrow, causing obvious frustration. To quote the data, one user clicked one of these arrows 308 times in only 8 minutes.

    Solution: Our tables are now implementing a control that catches users who are attempting this behavior, and redirecting them to a better user experience for finding the information they're after. Upon 5 or more Next/Previous arrow clicks, we now surface a control to get them where they want to go more readily and with low friction. We'll show this twice - once at 5 clicks, and once at 30. If they close it twice, we leave them to it until page reload. We've also added the ability to type in a page number to jump to exactly where you want. Try it out below:

    02

    Pain Point #2: Users are performing U-turns on a table record and its child records far too often. Think Location Details - users are frequently coming to these detail pages to check their service lines quickly, and then move on to the next one. The biggest issue with this particular workflow is that our locations list resets every time they leave and come back, so they’re losing some continuity and costing us a search each time they perform this action. There was one user who U-turned on one of these pages every 10 or so seconds for 45 straight minutes - that reads as a core workflow miss on our part.

    Solution: We’re implementing a new global paradigm for how users access information beyond a top-level list or record. When clicking on a table record on any page, the user now gets a flyout that includes their next-level down information at a quick glance. They have a series of actions they can perform from that view, and those actions will be curated based on the most common action users tend to perform on each page. Try it out.

    03

    Pain Point #3: We get dead clicks absolutely everywhere on our pages. Sometimes thousands in one session. This tells us that what is and isn’t interactable is not obvious - users click their mouse thinking something is going to happen, and become immediately frustrated when it doesn’t. Some pages like export log even have more dead clicks than views (1270 vs 1243 in the last month). The heaviest inventory user we tracked in that time was hitting a dead spot every two minutes for around two hours.

    Solution: Double down on the usability elements of our new patterns. Be overly explanatory via hover states when necessary. Full rows are now clickable within our table - dead clicks are no longer possible. We’re increasing the sizes of our click targets for links to give the user some wiggle room. An explicit rule we want to force is that every with a hover state does something, and everything that does something has a hover state. It reinforces the behavior we want for our users and teaches then when its safe and when its not safe to click. We’re also going to up our usage of tooltips in the platform. Try it out.

    04

    Pain Point #4: We aren’t reinforcing that the platform is actually responding to an action the user has taken. This is a classic UX flaw - the system status should always be communicated to a user and we’re taking strides in this system to improve that significantly. A lot of our rage clicks are simply because the platform was loading, and the user had no idea so they think their click just didn’t work (we’ve all been there). We fundamentally lack loading, in progress, or pending states in our platform today, and we’re addressing that.

    Solution: Adding in those in-progress states gives our user a clear picture of whats happening once they click something. Some as subtle as utilizing ‘pressed’ states more often, some as obvious as a literal spinner or progress bar within a button. Pulsing skeleton tables when things are loaded, controls for long-form user actions (think bulk edit or exports) that inform the user when a long job has finished, and more. These new patterns, applied globally, should massively help out our dead clicks problem. Try it out.

    Pain Point 5: Form fields aren’t communicating the state they’re in. Its not always obvious when a page is in an ‘edit-only’ state or when something is disabled entirely, as we’re not currently consistent with the presentation of those elements. Asset Details in particular is where this hurts us the most. Users are clicking a read-only area or something gated by a checkbox too many times. One user even clicked the same ownership checkbox in more than 30 individual sessions. That tells me that we’re misrepresenting what is and isn’t interactable.

    Solution: More robust componentry that communications its state to the users. Obvious, unmistakable treatment for disabled form fields. Rules for dependent fields: when one control disables another, the disabled one explains why. Extremely clear error states. We cover a lot of this today but improving in this area should have massive user benefits over the long term and reduce frustration significantly. Try it out.
